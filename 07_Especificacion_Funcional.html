1. Vision del Producto

1.1 Definicion Canonica

Nexus Assistant OS es un sistema operativo de trabajo conversacional que ingiere requerimientos de baja fidelidad (voz/texto via Telegram), recupera contexto de alta fidelidad (memoria de estado en Firestore), ensambla artefactos o ejecuta acciones, y notifica asincronamente el resultado.

3. Casos de Uso (24)

M-01: Telegram Gateway
CU-01: Recibir mensaje de texto
Actor
Operador
Precondicion
Operador autenticado por Telegram user_id
Postcondicion
Mensaje en cola Pub/Sub

Flujo: Telegram envia webhook → Cloud Function recibe → valida firma → extrae payload (user_id, timestamp, text) → publica en Pub/Sub → retorna HTTP 200 a Telegram (<2s)

Caso borde [CB-IDEM]: Telegram reenvia webhook por timeout. Deduplicar por update_id + operator_id. Procesar solo primera vez.
Criterio: ACK a Telegram en <2s. 0 mensajes duplicados procesados.

CODIGO bot.ts, telegram-update-guard.ts

CU-02: Recibir rafaga de mensajes
Actor
Operador envia 3+ mensajes en <3s

Flujo: Debounce de 2s agrupa mensajes del mismo user_id → concatena → publica como payload unico

Caso borde [CB-DEBOUNCE]: Si el 3er mensaje llega a los 2.1s, se procesa como segundo batch. Aceptable.
Criterio: Mensajes en rafaga se procesan como unidad coherente, no como 3 intenciones separadas.

DOC D1 seccion 6, D3 seccion 6

M-02: Voice Processing
CU-03: Transcribir nota de voz
Actor
Operador envia audio

Flujo: Telegram envia file_id → Cloud Function descarga audio → envia a Whisper API → recibe transcripcion → inyecta como texto en pipeline normal

Caso borde [CB-AUDIO60]: Audio >60s puede exceder timeout. Chunking: dividir en segmentos de 50s con 5s overlap, transcribir en paralelo, concatenar.
Criterio: Audio de 90s transcrito correctamente en <15s. Idioma espanol detectado automaticamente.

CODIGO audio.ts DOC D3 seccion 2

M-03: Intent Router
CU-04: Clasificar intencion
Actor
Sistema (automatico post-ingesta)
Postcondicion
Intent clasificado en <800ms

Flujo: Worker consume Pub/Sub → pasa texto a Groq Llama 3 8B con system prompt de clasificacion → recibe JSON: {intent, extracted_project_name, requires_web_search, requires_code_execution, urgency} → pasa a Orchestrator

Intents soportados: CHITCHAT PROJECT_QUERY RESEARCH ARTIFACT_GENERATION TASK_EXECUTION

Caso borde [CB-AMBIG]: Texto ambiguo ("haz eso") sin verbo ni proyecto. Router clasifica como CHITCHAT. Orchestrator responde pidiendo clarificacion.
Caso borde [CB-FALLBACK]: Groq no disponible. Circuit breaker conmuta a OpenRouter (Llama 3). Si tambien falla, Gemini. Si todos fallan, degradacion directa.
Criterio: 95% precision en test set de 100 mensajes. Latencia P95 <800ms.

CODIGO ecosystem/router.ts DOC D1 seccion 4, D3 seccion 2

M-04: Orchestrator
CU-05: Seleccionar modo de delegacion
Actor
Sistema

Flujo: Orchestrator evalua intent + urgency + complexity → selecciona modo:

  • SINGLE (≤15s): queries simples, CHITCHAT, PROJECT_QUERY basico
  • TERNA (≤30s): analisis multi-perspectiva, RESEARCH, ARTIFACT_GENERATION
  • COMMITTEE (≤60s): decisiones estrategicas, evaluaciones complejas

Degradation: COMMITTEE → TERNA → SINGLE → DIRECT

Criterio: Modo seleccionado en <100ms. Degradation automatica sin intervencion.

CODIGO ecosystem/committee.ts DOC spec.md, data-model.md

CU-06: Ensamblar contexto
Actor
Sistema
Dependencia
M-09 (Project State Engine) — CRITICO

Flujo: Orchestrator lee operator profile → identifica active_context_id → carga project.compressed_context (≤500 tokens) → carga short_term_memory (ultimos 15 turns) → pasa a Prompt Composer

Caso borde [CB-NOPROJECT]: No hay proyecto activo. Orchestrator procede sin project context. Si intent requiere proyecto, pregunta cual usar.
Criterio: Context retrieval en <200ms. 0 cross-project contamination.

CODIGO ecosystem/prompt-composer.ts, memory.ts

M-05: Prompt Composer
CU-07: Componer prompt maestro
Actor
Sistema

Flujo: Recibe intent + context + request → ensambla prompt: Constitution (reglas) + Operator preferences + Project context + Short-term memory + User request → aplica CP2 (prompt hardening) → envia a agente(s) seleccionado(s)

Token budget: single=4K, terna=12K, committee=20K. Si excede, truncar short_term_memory primero, luego compressed_context.

Criterio: Prompt ensamblado cumple token budget en >90% de requests. Truncamiento logeado.

CODIGO ecosystem/prompt-composer.ts, ecosystem/skill-composer.ts

M-06: Agent Pool
CU-08: Ejecutar agente Analyst

Flujo: Analyst recibe prompt + context → ejecuta analisis estrategico → genera respuesta estructurada (Minto pyramid, MECE) → retorna a Orchestrator

Scope: Strategic analysis, market evaluation, competitive intelligence

CODIGO agents/analyst/

CU-09: Ejecutar agente Researcher
Constraint
Researcher tiene IAM read-only. No escribe en projects ni memory.

Flujo: Researcher recibe query → ejecuta busqueda web → consolida fuentes → genera resumen con citaciones → retorna

Caso borde [CB-INJECT]: Pagina web maliciosa intenta prompt injection. CP3 escanea output antes de persistir. Si detecta instrucciones sospechosas, sanitiza y warn.
Caso borde [CB-LOOP]: Research entra en loop de navegacion. Max 5 iteraciones por query.
Criterio: Research multi-fuente con ≥3 fuentes citadas. 0 loops infinitos. 0 datos inyectados por prompt injection.

CODIGO agents/researcher/, tools/search-operational-knowledge.ts

M-07: Skill Engine
CU-13: Cargar y ejecutar skill

Flujo: Loader lee agent.md + skill.yaml al startup → valida con Zod schema → registra en runtime. En ejecucion: Orchestrator solicita skill → Skill Engine localiza → ejecuta workflow multi-step → valida cada step → retorna resultado

Caso borde [CB-INVALID]: Definicion de skill invalida. Loader skip + warn en logs. Otros skills funcionan normalmente.

Metricas: 24 skills, 96 workflows activos

Criterio: Skill invalida no bloquea startup. Workflow ejecuta steps secuencialmente con validacion per-step.

CODIGO ecosystem/skill-engine.ts, ecosystem/loader.ts, ecosystem/workflow-tool.ts

M-08: HIL Middleware A CONSTRUIR — H1-S2
CU-14: Solicitar aprobacion para accion L2

Flujo: Agente genera payload de accion → Orchestrator evalua permission level → Si L2: crea documento en pending_actions (status=AWAITING_APPROVAL, TTL=24h) → envia mensaje a Telegram con botones Inline [Aprobar] [Rechazar] → espera callback

Criterio: 100% de acciones L2+ pasan por HIL. 0 acciones ejecutadas sin aprobacion explicita.

DOC D3 seccion 3, Constitution Principio I

CU-15: Resolver accion pendiente

Flujo: Telegram envia callback_query → Sistema verifica callback.user_id == pending_action.operator_id → verifica status == AWAITING_APPROVAL → verifica expires_at > now → Si OK: actualiza status (APPROVED/REJECTED) → ejecuta o cancela + log en audit_log

Caso borde [CB-EXPIRED]: Operador aprueba despues de 24h. Sistema responde: "Esta accion expiro. Quieres que la re-proponga?"
Caso borde [CB-DOUBLE]: Operador hace doble-click en Aprobar. Idempotencia: verificar status antes de ejecutar.
Caso borde [CB-SPOOF]: Otro usuario intenta aprobar. Firestore rule + callback verification rechazan. Log en audit como intento sospechoso.
Criterio: Solo operator_id original puede resolver. Expiradas no se ejecutan. Doble-click es idempotente.

DOC D3 seccion 5, ADR-003

CU-16: Bloquear accion L4

Flujo: Orchestrator detecta L4 → bloqueo duro → log en audit_log → notifica operador: "Accion bloqueada: [descripcion]. Esta capacidad esta desactivada en esta version."

Criterio: 100% de acciones L4 bloqueadas. 0 excepciones.

DOC D2 seccion 8, D3 seccion 5

M-09: Project State Engine A CONSTRUIR — H1-S1
CU-17: Crear proyecto

Flujo: Router clasifica PROJECT_QUERY → Orchestrator detecta intencion de creacion → crea documento en coleccion projects con: name, owner_id, status=ACTIVE, compressed_context="" → confirma al operador → establece como active_context_id

Criterio: Proyecto creado y activo en <3s. Owner_id correcto.

DOC D1 seccion 2, D3 seccion 4

CU-18: Recuperar contexto de proyecto

Flujo: Router extrae project_name → Orchestrator busca en projects por name + owner_id → carga compressed_context → inyecta en Prompt Composer → responde con resumen de estado

Caso borde [CB-AMBIG-PROJECT]: Nombre ambiguo ("proyecto nuevo" x3). Orchestrator lista matches con detalles.
Caso borde [CB-EMPTY]: compressed_context vacio (proyecto recien creado). Degradacion: pide contexto al operador.
Criterio: Recuperacion en <3s. Contexto de proyecto inactivo 30d recuperado correctamente. 0 cross-project contamination.

DOC D3 seccion 2 (Gherkin), ADR-005

CU-19: Archivar proyecto inactivo
Actor
CRON automatico

Flujo: CRON diario evalua last_interaction de cada proyecto → Si > auto_archive_after_days (default 30): cambia status a ARCHIVED → no borra (projects nunca se borran)

Criterio: Archivado automatico funcional. Proyectos archivados no aparecen en context retrieval (pero si en busqueda explicita).

DOC D2 seccion 7, D3 seccion 4

M-10: Memory Manager
CU-20: Comprimir contexto nocturno
Actor
CRON nocturno

Flujo: Para cada proyecto ACTIVE con compressed_context modificado: LLM resume a ≤500 tokens → registra compression_log: {date, before_tokens, after_tokens, dropped_topics} → persiste en Firestore (transaction)

Caso borde [CB-CRON-FAIL]: Compresion falla mid-process. Firestore transaction revierte. Datos originales intactos.
Caso borde [CB-OVER500]: Resultado de compresion >500 tokens. Re-comprime con prompt mas agresivo. Si aun excede, trunca a 500 y log warning.
Criterio: compressed_context ≤500 tokens post-CRON. compression_log registrado. 0 datos perdidos sin log.

DOC D3 seccion 2, ADR-005

CU-21: Purgar memoria efimera
Actor
Firestore TTL automatico

Flujo: Documentos en short_term_memory con expires_at < now se eliminan automaticamente por TTL de Firestore

Criterio: Documentos expirados eliminados en <1h post-expiry. Max 15 turns retenidos por thread.

DOC D1 seccion 2, D3 seccion 4

M-11: Artifact Pipeline
CU-22: Generar artefacto HTML

Flujo: Router clasifica ARTIFACT_GENERATION → Orchestrator carga project context → delega a agente → agente genera contenido → Proposal Engine formatea como HTML → sube a Cloud Storage → genera URL firmada (7d expiry) → crea documento en artifacts (status=DRAFT, version=1) → asocia a proyecto → envia link a Telegram

Caso borde [CB-PARTIAL]: Generacion falla a mitad (LLM timeout). No guardar artefacto parcial. Reintentar 1 vez.
Caso borde [CB-QUOTA]: Storage quota excedida. Notificar sin perder artefacto en memoria.
Caso borde [CB-4096]: Respuesta >4096 chars (limite Telegram). Fragmentar en N mensajes o subir como .txt a Storage y enviar URL.
Criterio: URL firmada funcional por 7 dias. Artefacto versionado y asociado a proyecto. 0 parciales guardados.

CODIGO src/proposals/, controlled-deliverables.ts DOC D3 seccion 2

CU-23: Versionar artefacto

Flujo: Orchestrator identifica artefacto anterior por project_id + type → crea nueva version (version++) → marca anterior como ARCHIVED → nueva como DRAFT

Criterio: Versiones anteriores accesibles. Nueva version linked al proyecto.

DOC ADR-005, D3 seccion 2

M-12: Security & Observability
CU-24: Ejecutar pipeline de seguridad

Flujo:

  • CP1 (Input): sanitiza input, rechaza payloads malformados → HARD BLOCK
  • CP2 (Prompt): inyecta hardening en system prompt, verifica no prompt leak → HARD BLOCK
  • CP3 (Output): escanea respuesta por brand violations, prompt leak, datos sensibles → SOFT PASS (detecta y warn)
Caso borde [CB-CP3]: CP3 detecta posible brand violation pero respuesta es urgente. Entrega con warning interno. Log para revision posterior.
Criterio: 100% mensajes pasan CP1+CP2. CP3 detecta violations con >80% recall. 0 prompt leaks en output.

CODIGO security.ts, telegram-update-guard.ts DOC Constitution Principio III

12. Glosario

Agent
Nodo especializado que ejecuta tareas cognitivas atomicas dentro de un dominio acotado
Circuit Breaker
Patron de resiliencia que detiene llamadas a un servicio fallido para evitar cascada de fallos
Compressed Context
Resumen de ≤500 tokens del estado actual de un proyecto, generado por CRON nocturno
Constitution
Documento de gobernanza con 8 principios inmutables que rigen el comportamiento del sistema
Delegation Mode
Estrategia de asignacion de agentes: single (1), terna (3 paralelo), committee (5+tiebreaker)
HIL (Human-in-the-Loop)
Mecanismo de aprobacion humana para acciones que mutan estado externo
Minto Pyramid
Estructura de comunicacion: conclusion primero, luego soportes MECE
OpenClaw
Patron de agente autonomo mencionado en D6. No adoptado; Nexus usa State Machine.
Pending Action
Documento en Firestore que representa una accion propuesta esperando aprobacion humana
Pub/Sub
Sistema de mensajeria asincrona que desacopla ingesta de procesamiento
Skill
Capacidad ejecutable definida declarativamente en YAML, perteneciente a un agente
Terna
Modo de delegacion que invoca 3 agentes en paralelo para analisis multi-perspectiva
Work OS
Sistema operativo de trabajo — orquestador que retiene contexto y ejecuta tareas con aprobacion
Workflow
Secuencia de steps ejecutables dentro de un skill, con precondiciones y validacion per-step
