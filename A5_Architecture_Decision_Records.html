Architecture Decision Records
Nexus Assistant OS

6 decisiones arquitectonicas trazables

ADR-001 Topologia de 4 Planos Aceptado
Contexto
7 documentos proponen entre 4 y 7 capas.
Decision
4 planos (Ingesta, Control, Ejecucion, Persistencia) + 2 transversales (Seguridad, Observabilidad).
Justificacion
Mapea al repo, modelo de D3 (mas maduro), D6 confirma con 4 capas equivalentes.
Alternativas descartadas
  • 7 capas D2 (overhead)
  • 5 capas D1 (Egress no justificado)
Consecuencias
Simplicidad, posible subdivision en H3.
ADR-002 Firestore como Unica Persistencia Aceptado (revision en H3)
Contexto
D2 sugiere Redis, D3/D7/Repo solo Firestore.
Decision
Firestore para transaccional + semantica + efimera.
Justificacion
Reduce complejidad, ya implementado, suficiente single-tenant.
Alternativas descartadas
  • Redis (prematura)
  • PostgreSQL (cambio paradigma)
  • DynamoDB (vendor mismatch)
Consecuencias
Possible bottleneck semantic queries. Evaluar VDB en H2.
ADR-003 HIL via Pending Actions Aceptado (H1)
Contexto
Constitution exige aprobacion, repo no tiene HIL formal.
Decision
pending_actions en Firestore + Inline Buttons Telegram + TTL 24h + operator_id verification.
Justificacion
Habilita L2 seguro, patron definido en D3, bajo costo.
Alternativas descartadas
  • Chat libre (ambiguo)
  • 2FA externo (overengineering)
Consecuencias
Toda accion L2+ auditable. Latencia extra (button click).
ADR-004 n8n Spike H2 Diferido
Contexto
D6 propone n8n como ESB.
Decision
No en H1. Spike en H2 cuando haya integraciones.
Justificacion
Repo sin n8n. H1 sin integraciones. Complejidad prematura.
Alternativas descartadas
  • n8n dia 1 (overengineering)
  • Custom ESB (peor)
  • Zapier (vendor lock-in)
Consecuencias
Integraciones H1 API-directas. Si H2 agrega 3+ APIs, n8n se justifica.
ADR-005 Project State como Entidad Core Prioridad maxima H1
Contexto
D1-D3 coinciden: sin memoria de proyectos no hay Work OS.
Decision
Coleccion projects con compressed_context, knowledge_anchors, open_tasks, artifacts[], CRON.
Justificacion
Core differentiator. JTBD depende de esto. Todos los docs coinciden.
Alternativas descartadas
  • Context window infinita (caro, impreciso)
  • Knowledge graph (complejidad H3)
Consecuencias
Requiere CRON, UI gestion, integracion prompt-composer.
ADR-006 Token Budget per Request Propuesto H1-S4
Contexto
Sin presupuesto, query committee con contexto largo puede costar $2+ por request.
Decision
Budget: single=4K, terna=12K, committee=20K. Truncar short_term primero.
Justificacion
Costo predecible. Alineado con unit economics y graceful degradation.
Alternativas descartadas
  • Sin limite (impredecible)
  • Limite global diario (demasiado grueso)
Consecuencias
Posible truncamiento. Monitorear % truncados. Si >10%, subir budget.
