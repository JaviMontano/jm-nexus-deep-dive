MetodologIA Nexus Assistant OS — Architecture Deep Dive

04 — Mapeo de Flujos

Bounded Contexts, flujos E2E, matriz de integracion, puntos de falla y grafo de dependencias para Nexus Assistant OS.

TL;DR: 4 bounded contexts (Ingesta, Orquestacion, Ejecucion, Persistencia), 8 flujos E2E documentados, matriz de integracion, top-5 puntos de falla y grafo de dependencias. El flujo critico es Voz → Propuesta (F-05) — atraviesa los 4 bounded contexts con latencia de 20-45s.

01 — Taxonomia DDD: 4 Bounded Contexts

BC-INGESTA
BC-ORQUESTACION
BC-EJECUCION
BC-PERSISTENCIA
Bounded Context Responsabilidad Entidades Agregado Raiz
BC-INGESTA Captura de inputs (texto/voz), validacion, encolamiento TelegramUpdate, AudioPayload, PubSubMessage IngestaPipeline
BC-ORQUESTACION Routing, delegacion, composicion de prompts, degradation Intent, DelegationMode, PromptTemplate, CircuitBreakerState OrchestrationEngine
BC-EJECUCION Agentes especializados, skills, workflows, tools, HIL Agent, Skill, Workflow, Tool, PendingAction ExecutionContext
BC-PERSISTENCIA Estado de proyectos, memoria, artefactos, audit Project, Artifact, Memory, AuditEntry StateManager

02 — 8 Flujos E2E

F-01
Texto simple → Respuesta (CHITCHAT)
Latencia: <15s Level: L0 Riesgo: Bajo
Telegram → Webhook → CP1 → Pub/Sub → Worker → CP2 → Router (CHITCHAT) → Orchestrator → Agent → CP3 → Telegram Response
F-02
Audio → Transcripcion → Respuesta
Latencia: +5-10s (transcripcion) Level: L0 Riesgo: Medio
Telegram (audio) → Webhook → Whisper → Texto → ... F-01 pipeline

Chunking aplicado si audio >60s.

F-03
Query de proyecto → Contexto recuperado
Latencia: <15s Level: L0 Riesgo: Alto
Telegram → Ingesta → Router (PROJECT_QUERY) → Orchestrator → Firestore (projects) → Prompt Composer → Agent → Response

Dependencia critica: M-09 (Project State) — NO EXISTE AUN.

F-04
Research profundo → Sintesis
Latencia: 15-30s Level: L0 Riesgo: Medio
Telegram → Ingesta → Router (RESEARCH) → Terna Orchestrator → Researcher x3 → Web + KB Search → Consolidacion → CP3 → Response + citaciones

Riesgo: loops en agentes y prompt injection via fuentes externas.

F-05
Generacion de propuesta HTML Killer Use Case
Latencia: 20-45s (async) Level: L1 Riesgo: Alto
Telegram (voz) → Whisper → Router (ARTIFACT_GENERATION) → Orchestrator → Agent + Proposal Engine → HTML Gen → Cloud Storage → URL firmada 7d → Telegram link

Atraviesa los 4 Bounded Contexts. Riesgo: generacion parcial, timeout, HTML malformado.

F-06
Accion L2 con aprobacion HIL
Latencia: variable (humano en loop) Level: L2 Riesgo: Medio
Agent propone accion → Orchestrator evalua L2 → pending_action → Telegram Inline Buttons → Operador aprueba → Ejecutar → Audit log

Dependencia critica: M-08 (HIL) — PARCIAL.

F-07
Compresion nocturna de memoria (CRON)
Latencia: batch Level: N/A Riesgo: Medio
CRON trigger → Proyectos ACTIVE → LLM comprime → compressed_context ≤500 tok → compression_log → Persist (txn)

Riesgo: perdida de informacion en compresion agresiva.

F-08
Degradacion por falla de provider
Latencia: +2-5s por salto Level: L0 Riesgo: Alto
Request → Groq → CB OPEN → OpenRouter → Gemini (fallback) → DIRECT (ultimo recurso)

Recovery: Half-Open probe despues de cooldown configurable.

03 — Matriz de Integracion entre BCs

Origen → Destino Mecanismo Sincronicidad Datos
INGESTA → ORQUESTACION Pub/Sub Async Payload (user_id, text, timestamp)
ORQUESTACION → EJECUCION Function call Sync Intent + Context + Prompt
EJECUCION → PERSISTENCIA Firestore write Sync (txn) State mutations
PERSISTENCIA → ORQUESTACION Firestore read Sync Context retrieval
EJECUCION → INGESTA Telegram API Async Response message
